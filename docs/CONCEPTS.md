# TCAD-H Core Concepts

This document explains the three "roots" TCAD-H operates on, plus the
artifacts you will see in every Work Package. Read this once. It removes
a class of confusion.

## The three roots

TCAD-H is one binary (`tcad`) acting on three different file-system places.
Confusing them is the most common source of bugs.

### 1. Framework Root

Where TCAD-H is installed. Contains the scripts, templates, studio, and
this documentation.

```
~/.tcad-h/                 ← Framework Root (example)
├── bin/tcad
├── scripts/tcad_*.py
├── studio/
├── docs/
└── .protocol/             ← framework's OWN protocol (used to dogfood)
```

Resolved by `$TCAD_HOME` if set; otherwise the symlink target of `tcad`.

### 2. Target Root

The project repo where you are running TCAD-H. This is the codebase under
development. Its `.protocol/` is the live state.

```
/home/me/projects/my-app/  ← Target Root
├── backend/
├── frontend/
├── .protocol/             ← target's protocol (you bootstrap with tcad init)
│   ├── handoffs/
│   ├── status.json
│   ├── boundaries.yaml
│   └── ...
└── ...
```

Resolved by:

1. `--root <path>` CLI argument (if a script supports it)
2. `$TCAD_ROOT` env var
3. Walking upward from cwd looking for `.protocol/status.json`
4. `git rev-parse --git-common-dir` (returns the main repo's `.git`)
5. cwd as last resort

If you run `tcad ...` from inside a worktree, the resolver still finds
the target's `.protocol/` via step 4.

### 3. Worktree Root

The isolated git working tree created per Work Package + role. Lives
under `.protocol/worktrees/<wp>-<role>/` (gitignored).

```
my-app/.protocol/worktrees/WP-001-add-auth-backend/
├── backend/         ← same project, but on a separate branch
├── frontend/
└── ...
```

A worktree shares the same `.git` directory as Target Root (that's how git
worktrees work), but its working tree is independent. Two worktrees on
two branches can co-exist on disk without conflict.

### Mental rule

| You are running `tcad ...` from | TCAD-H acts on |
|---|---|
| anywhere with `$TCAD_HOME` set explicitly | Framework Root |
| anywhere with `$TCAD_ROOT` set explicitly | that path as Target |
| inside Target Root | Target |
| inside a worktree under Target | Target (via git common dir) |
| outside any TCAD-H repo | falls back to cwd; may produce nothing useful |

The `tcad doctor` command always reports which root it resolved.

## Per-Work-Package artifacts

A closed WP folder looks like this:

```
.protocol/handoffs/WP-NNN-slug/
├── .tcad_wp.json              ← metadata: profile (lean/verbose), role, required files
├── 01_goal.md                 ← human-authored intent
├── 02_allowed_files.md        ← what the worker may edit (path firewall)
├── 03_forbidden_files.md      ← what the worker must NOT edit
├── 05_worker_prompt_<role>.md ← the prompt the worker reads
├── 10_acceptance_criteria.md  ← how to know it's done
├── 11_worker_summary.md       ← worker output (must include 'NEXT STEP')
├── 12_delta.md                ← optional: worker discovered scope expansion
├── 13_blockers.md             ← optional: worker stopped, needs human
├── 14_review_result.md        ← optional: reviewer verdict
├── 15_diff.patch              ← captured by tcad close
├── 16_code_graph.json         ← generated by tcad graph build
├── 17_semantic_graph.json     ← deferred (Phase 2.5b)
├── 18_impact_map.md           ← deferred
├── 19_mermaid.md              ← generated by tcad graph build
├── 20_reviewer_focus.md       ← deferred
├── 21_open_questions.md       ← raised by reviewer
├── close_report.json          ← gate outcomes + smoke results
└── review_report.json         ← reviewer findings (when run)
```

Numbered prefixes are intentional: when you list the folder, the order
reflects the temporal phase of the Work Package.

## Roles

A WP is created with `--role`. The role determines which prompt file the
worker reads.

| Role | File generated | Typical CLI / model |
|---|---|---|
| `backend` | `05_worker_prompt_backend.md` | OpenCode + Kimi / GPT |
| `frontend` | `06_worker_prompt_frontend.md` | OpenCode + Qwen |
| `tests` | `07_worker_prompt_tests.md` | OpenCode + Minimax |
| `reading` | `08_worker_prompt_reading.md` | DeepSeek long-context |

The Conductor (you driving `tcad`) is usually Claude Code. The Reviewer
must be a different model than the worker.

## Lean vs Verbose Work Packages

| Mode | Files generated | When to use |
|---|---|---|
| `--lean` (default for new repos) | 5: goal, allowed, forbidden, worker prompt, acceptance | Fast iteration, small features |
| verbose (default if `--lean` omitted) | 12: full template incl. context, reviewer prompt, existing decisions, etc. | High-risk features, larger refactors |

Both modes produce `.tcad_wp.json` so `tcad doctor` and the conductor know
which set of files is required.

## States the Conductor drives

```
IDLE
  → INTAKE (human asks for change)
    → SPEC_DRAFT (intent captured)
      → HANDOFF_GEN (WP files generated)
        → WORKER_BRIEF (worker has prompt + worktree)
          → WORKER_DONE | REWRITE_WP | ESCALATE
            (worker wrote 11_summary | 12_delta | 13_blockers)
          → ATLAS_GEN | REVIEWING
            → PASS | PASS_WITH_NOTES | FAIL
              → LOG | FIX_REQUEST | ESCALATE
                → DONE
                  → IDLE
```

You can drive transitions manually with `tcad conduct transition <STATE>`.
A bad transition (skipping states, lacking required artifact) is rejected
with exit 2 and a human-readable reason.

---

## What never changes

TCAD-H's iron rules apply at every root:

1. No model receives conversation history.
2. The Conductor never writes production code.
3. The Reviewer is never the Implementer.
4. Open blocking questions halt progress.
5. No file edited outside the active Work Package's `02_allowed_files.md`.

Implementation details may evolve. These five do not.
